## 1. 要解決什麼

**目標**：桌面版後台連 `exam-server` 時走 WireGuard 隧道，**但使用者不必安裝、不必開啟、不必知道它存在**。

**主公 給的理由（2026-08-14 議事廳）**：

1. **選 WireGuard 的理由是資安稽核** —— **TCP 8787 不對院內實體網卡暴露，只可經 overlay 存取**
   ⚠️ **不要講成「什麼都沒開」**：UDP 51820 是開著的（WireGuard 走 UDP）。
   那句在稽核上站不住，已於 `exam-server` `eeb5c21a` 一併改掉安裝文件裡的同一句。
2. **要內嵌進 app 的理由是教育成本** —— 「多裝一個東西」對 20 位非技術使用者的成本太高

⚠️ **這兩個理由要一起看**：若只為了安全，官方 WireGuard 客戶端就夠了；
**是「零教育成本」這個要求，才把方案推向內嵌。**

### 3.1 ⭐ `exam-server` 與桌面版的關係——**這一格改變了整份規劃的框架**

`exam-server` 就是 `server-foundation`，它的目標寫在 `plan.md:7`：

> 「`server-foundation` 要讓**同一個** Windows 桌面 App，可以依部署需求使用**不同的資料與檔案後端**，而不需要修改 UI 或業務流程。」

三種 deployment profile（`plan.md:11-13`）：

| profile | 現況 |
|---|---|
| `cloudflare-d1-r2` | **就是現在的 `exam-control`**（`control.exam.tw`） |
| `vps-mysql` | **就是這次要建的院內這台** |
| `google-sheets-drive` | 未使用 |

⇒ **不是「搬家」，是「多一種可選後端」。** 桌面版要能指向其中任一個。

### 3.3 🔴 攔路石：API 請求是 **webview 發的**，Rust 攔不到

```
src/auth/tauri-ports.ts:63        await fetch(toAbsoluteUrl(request.path, override), {…})
src/ui/authenticated-app.tsx:84   await fetch(toAbsoluteUrl(request.url, override), init)
src-tauri/                        沒有 reqwest、沒有 http plugin、Rust 側完全不發 HTTP
```

⇒ **把 WireGuard 內嵌進 Rust，那兩個 `fetch` 一個都不會經過隧道**——它們直接走作業系統網路堆疊。

⚠️ **這一格若沒先發現，會做到「東西都接好了、封包卻還是走原路」才爆。**

### 3.4 ⭐ 好消息：組網域的地方只有一處

`base-url.ts:143-145` 的註解自己寫著：

> 「這是唯一該把它接上網域的地方 —— 集中一處，才有可能斷言『沒有別的地方在決定網域』。」

⇒ **要改 base URL，只有 `toAbsoluteUrl()` 一個咽喉點。** 這對本案非常有利。

### 3.5 技術可行性（已查證）

`tokio-wireguard`：

- 提供 `TcpStream`／`TcpListener`／`UdpSocket`，**API 對齊 `tokio::net`**
- 文件明寫：**不需要 TUN 裝置、不需要 root／管理員權限**

⚠️ **`boringtun` 不能單獨用**——它只實作 WireGuard 協定本身，**不含網路堆疊與通道層**。
`tokio-wireguard` 的價值就是幫我們把那兩層接起來了。

## 4. 提議架構

```
桌面版 (Tauri)
┌──────────────────────────────────────────────────┐
│  webview                                          │
│    fetch("http://127.0.0.1:<固定高位埠>/api/…")       │
│              │                                    │
│  ────────────┼─── Rust (src-tauri) ───────────    │
│              ▼                                    │
│    本機轉送口（app 啟動時起、關閉時收）              │
│              │                                    │
│    tokio-wireguard 隧道（使用者空間，無驅動）        │
└──────────────┼───────────────────────────────────┘
               │ UDP 51820
               ▼
      exam-server（院內）10.99.0.1:8787
```

**為什麼是「本機轉送口」而不是「把傳輸層搬進 Rust」**：

| 做法 | 要改的東西 |
|---|---|
| **本機轉送口**（提議） | TS 側只改 `toAbsoluteUrl()` 的 base URL；兩個 `fetch` 一行不動 |
| 全搬進 Rust | 兩個 `fetch` 改成 `invoke`，整個 request/response 型別要跨 IPC 重做 |

⇒ **前者小得多**，而且這是 `onetun` 那類工具既有的形狀，不是自創。

### 4.1 🔴 它是 **HTTP gateway**，不是 TCP relay（初稿混了兩種，已定案）

初稿一邊畫「轉送口」（像是 byte-for-byte 的 TCP relay），一邊又要求檢查 token
——**要檢查 token 就得看得懂 HTTP**，兩者不能並存。**明確定案為前者：一個很薄的 localhost HTTP 反向代理。**

它**必須**處理：

1. **CORS 與 preflight** —— 登入後的請求帶 `Authorization: Bearer …`，
   寫入還帶 `Content-Type: application/json`。⚠️ **這兩個都不是 safelisted header ⇒ 瀏覽器會先送 `OPTIONS`。**
   gateway 不處理 preflight 的話，**請求根本不會發出去**，而錯誤訊息只會說「網路錯誤」。
2. **驗本機 token** —— app 啟動時產生，只有自己知道；**驗完要移除再往上游送**
3. **寫死上游** —— **只能去 `10.99.0.1:8787`**
4. 必要時改寫 `Host` 標頭

⚠️⚠️ **絕對不做**：SOCKS、`CONNECT`、任意目的地轉送。
⇒ 否則同機任何程式都能拿 gateway 當跳板，**去探索整個 `10.99.0.0/24`**——
那會把「裝置准入」這層完全架空。

### 4.2 🔴 埠號用**固定高位埠**，不是動態埠（初稿的動態埠與 CSP 衝突）

⚠️ **Tauri 的 CSP 是建置期決定的**，runtime 才挑的埠**沒辦法事先精確列進 `connect-src`**
⇒ 最後只能放寬成一整段 localhost 範圍，**那正是初稿 §5.2 自己說「不可以」的事**。

⇒ **定案**：固定高位埠、**app 啟動時自己先 bind**、**bind 不到就 fail closed 並明講原因**。
（隨機埠本來也只防猜、防不了列舉，真正的防線是本機 token。）

## 4.3 ⭐ 註冊機制（**主公 設計、2026-08-14 定案**）

### 為什麼這個設計成立——它解掉了「註冊要開 TCP 埠」那個死結

初稿第 9 節說「自己蓋註冊機制要開 TCP 埠，抵銷選 VPN 的初衷」。**這個設計繞過了**：

> **伺服器是「去 CF 撈」，不是「等人來送」。**
> ⇒ **全程沒有任何 inbound 連線到 exam-server，稽核那個性質完整保住。**

而 `/li41` 本來就是 exam-control 生產路由（`exam-control/wrangler.jsonc:224` 實查），**現成管理面，不必新蓋**。

### 分層（主公 原話）

> **用戶端能決定 Google 帳號能不能用 app；我（/li41）決定 app 能不能連 server。**

### 流程

```
① 裝好 → 第一次開啟 → Google 登入（對 CF，不是對 exam-server）
② 查本機有無金鑰；沒有就產金鑰對，私鑰存 Windows DPAPI
③ 送 {信箱, 公鑰, 機器名, 資產編號} 到 CF
   → 畫面顯示「等待開通中」，並告知大約多久
④ 主公 在 /li41 審核 → 核准
⑤ exam-server 上的程式撈 CF → **整份同步** wg0.conf → `wg syncconf`
⑥ app 連得上
```

⚠️ **③～⑥ 之間有一段 app 連不上的空窗**，必須在畫面上講清楚，
否則使用者會以為壞了。**不要為了消掉空窗去做「自動推送」——那會需要 inbound。**

### 🔴 四個實作上不能省的細節

| # | 要求 | 不做會怎樣 |
|---|---|---|
| **E1** | 審核畫面要顯示**信箱＋機器名＋資產編號＋送出時間＋來源 IP**，並標示**這個信箱是不是已經有別的公鑰** | 只看到一串亂碼公鑰 ⇒ 只會一律按核准，**這道關卡變成儀式** |
| **E2** | 撈回來要**整份同步，含刪除** | ⚠️ **撤銷永遠傳不過去**——CF 上取消了，那台照樣連得進來且無徵兆 |
| **E3** | 用 `wg syncconf wg0 <(wg-quick strip wg0)`，**不要 `systemctl restart`** | restart ⇒ **20 台全部斷線重連**，每加一人全院閃一次 |
| **E4** | 那支程式持有 CF 憑證且以 root 寫 `/etc/wireguard` ⇒ **新的高權限元件** | — |

### ⚠️ E4 帶來的信任方向改變（主公 已知悉並接受）

| | 加一個 peer 需要什麼 |
|---|---|
| **以前** | 那台伺服器的權限 |
| **以後** | **CF 管理面的權限** ⇒ `/li41` 被攻破可往院內伺服器塞 peer |

⇒ **主公 2026-08-14 表示接受**（`/li41` 有認證、是他自己的管理面）。**記在這裡是要它是自覺的決定。**

### 排程還是手動？

⚠️ **未定案。** 排程 ⇒ 使用者等 N 分鐘、但程式要長期持有 CF 憑證；
手動 ⇒ 主公 多跑一次、憑證只在跑的時候用。
**20 台的規模我傾向手動**，但這一格留給實作時決定。

## 5. ⚠️ 已知代價（**不是零成本，請逐條看**）

### 5.1 綁 `127.0.0.1` ⇒ 那台電腦上其他程式也碰得到 gateway

gateway 一旦開著，**同一台機器上的其他程式（或其他登入使用者）都連得到它**。

⚠️ **這是真實的性質改變**，跟官方客戶端不同（官方那個也是全機生效，但至少是使用者自己開的）。

**四層防線**（⚠️ 修訂 2 之前寫成三層、且把 Google 登入寫成「真正的門」，兩者都是錯的框法）：

| 層 | 擋什麼 | **誰維護** |
|---|---|---|
| **① WireGuard peer** | **裝置准入** —— 沒有金鑰的機器連不到、掃不到 | **主公（`/li41`）** |
| **② 本機 token** | **本機 gateway 准入** —— 同機不知情的程式進不來 | app 自己（啟動時產生） |
| **③ Google 簽章票** | **認證：你是誰** | Google ＋ CF |
| **④ exam-server 權限表** | **授權：你能做什麼** | ⭐ **貴院自己的管理員** |

⚠️⚠️ **①和④是不同的人在管**（2026-08-14 主公 指出，修訂 2 補入）：

> **主公 決定「哪台機器連得到 server」；貴院管理員決定「哪個帳號能用、能用什麼」。**

⇒ **隧道通了 ≠ 能做事。** 一台剛核准的機器、拿著有效 Google 身分連上來，
**若那個帳號沒被貴院管理員開通，一樣什麼都做不了。**

⭐ **這與「exam-server 只有資料庫和提供 api」完全一致**——
「誰能做什麼」是**資料**，不是登入機制。⇒ `users` 表留著，**只是不存密碼**。

⚠️ **②擋得住不知情、擋不住刻意**（同機程式理論上讀得到 token）。
⇒ **所以 4.1 的「寫死上游、不做任意轉送」才重要**：即使有程式碰到 gateway，
**它也只能打 `10.99.0.1:8787` 這一個目的地，不能拿它當跳板探索內網。**

### 5.1b 🔴 四層各自失敗時，**畫面必須分辨得出來**

「用不了」有**四種完全不同的原因，而且要找的人不同**：

| # | 狀態 | 該顯示什麼 | **該找誰** |
|---|---|---|---|
| 1 | 還沒 Google 登入 | 請登入 | — |
| 2 | **這台還沒被主公 核准**（層①） | 「等待開通中，已送出申請」 | **主公** |
| 3 | **帳號還沒被貴院管理員開通**（層④） | 「您的帳號尚未開通」 | **貴院管理員** |
| 4 | 隧道斷線（睡眠醒來、換網路） | 「連線中斷，重試中」 | 通常自己會好 |

⚠️⚠️ **這四種若全都顯示「無法連線」，排查會很痛苦**——
使用者打電話給主公，而問題其實在他們自己管理員那邊；或反過來。

⇒ **成本很低（幾段文案＋分辨狀態），不做的話會一直接到打錯的電話。**

⚠️ **另一格別留到上線那天才發現：第一個管理員誰開通？**
帳號要有人開通，但第一個人沒人能開通他 ⇒ **必須預先種進去（seed）。**

### 5.2 會動到三道現有守門

桌面版 verify 裡有這三步（實查自 pre-push 輸出）：

- `P8.5 CSP 診斷自我檢查` / `Tauri CSP 最小政策自我檢查`
- `JS URL host allowlist 自我檢查`
- `產物零外連資產`

指向 `http://127.0.0.1:<埠>` 會碰到它們。
⚠️ **要改的是設定與登記，不是放寬閘門**——若發現「只能靠放寬閘門才過」，那是設計有問題的訊號。

### 5.3 明文 HTTP 走 localhost

轉送口與 webview 之間是 `http://`（不是 https）。
在隧道外的那一小段是**同一台機器內的 loopback**，一般認為可接受，
⚠️ 但**稽核時會被問**，要準備好說法（「未離開本機、且真正的傳輸加密由 WireGuard 提供」）。

## 7. 探針計畫（**兩根，不是一根**）

⚠️ **初稿只有一根、而且判準訂得太寬**（`/health` 200 就宣告通過）。
**200 只證明了隧道，沒證明瀏覽器那一側。** 改成兩根：

### P1 — 傳輸層探針

> **Windows 上**，Rust 側用 `tokio-wireguard` 連上 `exam-server`，打 `/health` 拿到 **200**。

**不做**：gateway、TS 整合、閘門、UI。
**產出**：U1、U2、U6 的答案（U3、U5 順手觀察）。⚠️ U4 已在紙上查完（3.6），探針不必再問。

### P2 — 瀏覽器邊界探針（⭐ **這根才是真正的風險所在**）

> **webview `fetch` → localhost gateway → 隧道 → `exam-server`**，
> 打一支**帶 `Authorization` 的唯讀 API**，拿到正確資料。
> 然後**做一次睡眠→喚醒、以及換網路**。

⇒ **這一根一次驗完 U7（CORS/preflight）、U8（CSP）、U3（斷線重連）、Host 標頭、Bearer、HTTP parser。**

⚠️ **P1 過了不代表可以開工，要 P2 也過。**

**判準**：
- **兩根都過** → 開正式工單
- **P1 不過** → 退回官方客戶端 ＋ 桌面版偵測提示（成本低很多，見第 9 節）
- **P1 過、P2 不過** → 視卡在哪：CSP／CORS 通常有解，但要重新評估 gateway 的形狀

## 8. 決策清單（✅ 已定案 5 項／🔴 待拍板 2 項）

### D1. **前置缺口要不要一起做？**

桌面版現在**沒有連 `exam-server` 的能力**（3.2）。內嵌 WireGuard 是「怎麼連」，
但「**能不能指向它**」是更前面的一步，目前是寫死 CF。

⇒ **兩件事要一起規劃，還是先做 profile 切換、隧道之後再說？**
（我的看法：**先做 profile 切換**。沒有它，隧道通了也沒東西可連。）

### D2. **接受 5.1 那個代價嗎？**

本機轉送口 ⇒ 同機其他程式也能借隧道。
⇒ 若這一格不能接受，內嵌這條路要重新想（要走 IPC 全搬進 Rust，成本高很多）。

### D3. **押不押 `tokio-wireguard`？**（⚠️ 實查後這題比初稿嚴重）

**兩年沒發版、28 星、無上游可指望**（3.6）。押的話要接受「出事自己修」，
並且**釘 git commit 而非版號**（3.7）。
⇒ 不押的替代是自己疊 `boringtun`＋`smoltcp`——**等於重寫那 2,400 行**，我不建議。

### D4. **探針由誰做？**

王陽明 手上 `WO-EXAM-FORM-A-1` 在跑。選項：排在他後面／給岳飛（待額度）／我自己做。

### ✅ D5. **Peer 金鑰怎麼發？** —— **已定案（2026-08-14 主公）**

**金鑰在安裝後第一次開啟時、就地產生**，私鑰進 Windows DPAPI，**永不移動**。
公鑰經 CF 送審、由 exam-server 主動撈回。**完整流程與四個實作細節見 4.3。**

⭐ **這個做法比初稿好**：初稿是「主公 產金鑰 → 把含私鑰的 `.conf` 送給使用者」，
**中間那段運送（信箱／隨身碟／聊天視窗）就是風險。主公 的做法把它整個拿掉了。**

⚠️⚠️ **絕對不可以把同一把私鑰編進 EXE**——那等於 20 台共用一把，撤銷只能全撤、稽核分不出是誰。

⚠️ **待辦**：`exam-server/doc/almalinux-10-安裝.md` 的〈新增一台桌面電腦〉那節
**寫的是官方客戶端版**（第③步是「把 `.conf` 交給使用者」）——**內嵌版沒有那個檔，該節要重寫。**

### ✅ D6. **TCP relay 還是 HTTP gateway？** —— **已定案：HTTP gateway**（2026-08-14 主公）

理由見 4.1：**檢查本機 token 與回應 CORS preflight 都必須看得懂 HTTP**，延長線做不到。

### ✅ D7. **exam-server 的身分來源** —— **已定案（2026-08-14 主公）**

> 主公 原話：「exam-server 是只有資料庫和提供 api，**用戶登入的是桌面版**。」

**定案的形狀**：

```
使用者 ── Google 登入 ──► 桌面版（CF 那側驗身分、發一張 RS256 簽章票）
                             │  每個 API 請求帶著那張票
                             ▼
                        exam-server：只驗簽章，不做登入
```

- ❌ exam-server **沒有**登入畫面、**不存**密碼
- ✅ **只驗一張票**，用預先放好的公鑰**離線驗**——⚠️ **不必連 CF，院內對外斷線也能用**
- ✅ 稽核日誌因此記得到「是誰」

⚠️ **但「驗票拿到身分」只是認證。** 授權（能做什麼）仍由 **exam-server 自己的 users／權限表**決定，
**而那張表是貴院管理員維護的**（見 5.1 第④層）。⇒ **驗票 → 查表 → 決定准不准**，兩步都要。

**⭐ 這不是新發明**：`exam-control/src/auth/authorization-license.ts:19` 已經在用 RS256
（control 發、runtime 驗），**同一套形狀再用一次**。

#### ⚠️ 為什麼「驗身分」這件事不能省

**隧道證明的是機器，不是人。** 而且跟 4.1 的本機 gateway 直接相關：

> gateway 綁 `127.0.0.1` ⇒ 那台電腦上**任何程式**都連得到它。
> 若 exam-server 只認「從隧道進來就放行」⇒ **那支程式穿過隧道就拿到全部 API，不需要任何帳號。**

⚠️ **桌面版的登入擋的是「人」，擋不到「不經過桌面版 UI 的請求」。**

#### ⚠️ 現況與定案相反，這是要動工的

```
exam-server  apps/api/src/app.ts:373                → "/auth/login"
exam-server  packages/auth/src/password-hasher.ts   → Argon2PasswordHasher
exam-server  README.md:24                           → MySQL：items、users、…
```

⇒ **它現在有自己的 argon2 密碼登入與 users 表。**
**這一格是「把現有的登入換成驗票」，不是「幫它加登入」。**
`plan.md:3` 也把 OAuth 列在未完成項。

⚠️ **這件事與 WireGuard 那條線互相獨立、可分開排，但不能不排**——
否則做完隧道會發現：**機器進得來，卻不知道是誰進來的。**

#### 🔴 它同時決定了離職風險

主公 先前說「離職不用擔心，還有 Google 登入那道」——
**那句話只在 D7 落地後才成立**（身分來自 Google 票 ⇒ 帳號停用，票就發不出來）。
**若維持 argon2 密碼，停用 Google 擋不到 exam-server 的登入。**

## 9. 沒有選的方案與理由（免得日後再問一次）

| 方案 | 為何不選 |
|---|---|
| 官方 WireGuard 客戶端，使用者自己裝 | 可行且最穩，**但主公 判定教育成本太高**。⚠️ **這仍是探針失敗時的退路。** |
| 限院內網段的白名單 | **仍要開 TCP 埠**，稽核那一格省不掉——而那正是選 VPN 的唯一理由 |
| 公開 HTTPS | 對外服務才需要；本案是院內服務 |
| 桌面版問 CF 要伺服器位址 | 新增「同棟樓服務卻要先連外網」的相依；且那位址不是秘密 |
| 自己蓋註冊機制（首次連線交換金鑰） | **WireGuard 不允許**——伺服器必須先有那把公鑰，未知公鑰直接丟包；自己蓋要開 TCP 埠，抵銷初衷 |

## 10. 建議的執行順序

**D5／D6／D7 已定案** ⇒ 剩下的順序：

```
D1 profile／後端切換     ← 沒有它，隧道通了也沒東西可連
      ↓
P1 傳輸層探針            ← Windows + tokio-wireguard + handshake + TCP
      ↓
P2 瀏覽器邊界探針        ← webview → gateway → 隧道 → 帶 Authorization 的真 API
      ↓                    ⭐ 這根才是真正的風險所在
   ┌──┴──┐
   ▼     ▼
localhost   註冊機制（4.3：CF 送審 + server 撈回 + syncconf）
HTTP gateway
   └──┬──┘
      ↓
   D7 身分票（exam-server 由 argon2 換成驗 RS256 簽章）
```

⚠️ **D1 之所以排最前**：它本來就是獨立存在的技術債（release 寫死 CF），
**跟 WireGuard 做不做都無關**——WireGuard 解的是「怎麼到那裡」，不是「要去哪裡」。

⚠️ **D7 排最後，但不能不排。** 它跟 WireGuard 互相獨立，
可是**少了它，做完隧道也只知道「哪台機器」、不知道「誰」**——而稽核問的正是後者。
